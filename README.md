# wasm-football

Experiment sources, deployment manifests and analysis for the master's thesis
**"Energy Efficiency of WASM-Based Applications in Kubernetes"** (HFT Stuttgart).

The study compares one REST API - a football statistics service over players,
teams and matches - implemented in three languages and deployed in six variants
on the same single-node Kubernetes cluster. Every variant is distributed as an
OCI artifact through the same registry and scheduled by the same containerd;
only the runtime shim differs, so the comparison is between runtimes rather than
between delivery mechanisms.

Energy is read from the host's RAPL counters by Kepler, load is generated by k6
from a separate workstation, and all metrics are stored in VictoriaMetrics. The
notebooks in `notebooks/` derive every figure of the evaluation chapter from
those recorded metrics.

> The Kotlin reference implementation lives in a **separate** repository,
> [exruos/spring-football](https://github.com/exruos/spring-football). This
> repository holds the Rust and JavaScript implementations, the testbed, the
> load scripts and the analysis.

## Deployment variants

| Target (`-Target`) | Image | Runtime | Built by |
| --- | --- | --- | --- |
| `oci-spring` | `football-kotlin:spring` | JVM in a container (runc) | `spring-football` repo |
| `oci-native` | `football-kotlin:native` | GraalVM native image | `spring-football` repo |
| `oci-axum` | `football-rust:axum` | Rust/Axum in a container | `spin-rust/container/Dockerfile` |
| `oci-node` | `football-js:node` | Node.js in a container | `spin-js/container/Dockerfile` |
| `wasm-rust` | `football-rust:wasm` | Wasm component, Spin shim | `spin-rust/spin.toml` |
| `wasm-js` | `football-js:wasm` | Wasm component, Spin shim | `spin-js/spin.toml` |
| `wasm-rust-components` | `football-rust:wasm-components` | 3 Wasm components, split | `spin-rust/spin.components.toml` |

`wasm-rust-components` is the componentization control: the same Rust sources
packaged as three route-scoped components instead of one monolith.

## Prerequisites

On the workstation (the machine that drives the experiment):

- `kubectl` and `helm`
- `docker` for the container variants, and a local `spin` for building and
  pushing the Wasm ones. The SpinKube plugin is required as well:

  ```powershell
  spin plugins update
  spin plugins install kube
  ```
- `k6` for load generation
- `uv` for the notebooks
- `nix` with flakes enabled, and `nixos-anywhere`, if you deploy the hosts
- `k3d` only if you want the local development cluster

PowerShell 7+ is assumed; the scripts are `.ps1`.

## Configure this before anything else

Several values are pinned to the author's testbed and **must** be changed.

**1. Host names.** `hetzner-metal` is the benchmark server (bare metal, the
machine under measurement) and `hetzner-vm` is the cloud instance hosting
VictoriaMetrics. Both are plain hostnames resolved on the workstation - set them
in your `hosts` file or in DNS to the two machines' addresses. They appear in:

| File | Setting | Meaning |
| --- | --- | --- |
| `k6/load-test.js` | `const baseUrl` | where k6 sends load |
| `k6/benchmark.ps1` | `$VictoriaMetricsUrl` | where k6 writes its metrics |
| `notebooks/benchmark_extract.py` | `endpoint` | where the analysis reads metrics |
| `notebooks/rtt.py` | `VM` | same |
| `nixos/k3s.nix` | `--tls-san` | the API server certificate's SAN |

**2. The in-cluster remote-write target.** `k3s/vm-values.yaml` points vmagent at
a literal IP rather than a hostname, because it is resolved from inside the
cluster. Change `remoteWrite[0].url` to your metrics host.

**3. Your SSH key.** `nixos/configuration.nix` hard-codes the author's public key
under `users.users.root.openssh.authorizedKeys.keys`. Replace it, or you will not
be able to log into the machine you just installed.

**4. Credentials.** `kustomize/base/app-secret.yaml` ships `postgres/postgres`,
and `nixos/vm.nix` ships Grafana `admin/admin` plus a literal `secret_key`. These
are acceptable on an isolated benchmark host and are not acceptable on anything
reachable.

## Testbed A - the remote hosts (used for the measurements)

Both machines are installed from this flake with
[nixos-anywhere](https://github.com/nix-community/nixos-anywhere), onto a target
booted into any NixOS-capable rescue system. The hardware report is generated on
first install and then committed, so later rebuilds are reproducible.

Benchmark server:

```bash
nixos-anywhere --flake .#bench \
  --generate-hardware-config nixos-facter ./facter-bench.json \
  root@hetzner-metal
```

Metrics host:

```bash
nixos-anywhere --flake .#vm \
  --generate-hardware-config nixos-facter ./facter-vm.json \
  root@hetzner-vm
```

The disk layout comes from `nixos/disk-config.nix` via disko, which
**partitions and formats the target disk** - point it at a machine you intend to
wipe.

Subsequent changes do not need nixos-anywhere again:

```bash
nixos-rebuild switch --flake .#bench --target-host root@hetzner-metal
```

`.#bench` brings up K3s with the Spin shim registered as a containerd runtime, a
zot registry on port 5000, and Traefik with the Gateway API provider enabled.
`.#vm` brings up VictoriaMetrics (port 8428, one year retention) and a Grafana
provisioned against it.

### Cluster add-ons

With `kubectl` pointed at the benchmark cluster, install cert-manager, the Spin
operator, the VictoriaMetrics stack, Kepler and KEDA:

```powershell
cd k3s
./remote-cluster.ps1
```

The script prints the current kube context and asks for confirmation first - read
it, since it installs into whatever cluster your kubeconfig points at.

Then restart K3s once so that containerd picks up the shim configuration, as the
script reminds you at the end:

```bash
ssh root@hetzner-metal systemctl restart k3s
```

Finally apply the Kepler scrape config, which `remote-cluster.ps1` does *not* do:

```powershell
kubectl apply -f k3s/kepler-scrape.yaml
```

> **Cold-start runs need a faster scrape.** Kepler's counter advances about once
> per second, which is too coarse for a cold start lasting 2–10 s. Before the
> coldstart scenario, swap in the high-resolution pair (100 ms monitor interval,
> 500 ms scrape) and swap back afterwards:
>
> ```powershell
> helm upgrade kepler <chart> -n monitoring -f k3s/kepler-values-coldstart.yaml
> kubectl apply -f k3s/kepler-scrape-coldstart.yaml
> ```

## Testbed B - a local cluster (development only)

This gives a working Spin-capable cluster on the workstation. It has no Kepler,
no KEDA and no energy measurement, so it is for checking that a variant deploys
and answers correctly - not for producing results.

Start a registry container first; the script expects one named `registry` and
only connects it to the k3d network:

```powershell
docker run -d -p 5000:5000 --name registry registry:2
cd k3s
./local-cluster.ps1
```

The cluster publishes the gateway on `localhost:8081`.

## Build the database image

All variants share one pre-migrated Postgres image, so schema, indexes and data
volume are constant across the experiment and migration cost is excluded from
every measurement. The recipe is in [`db/README.md`](db/README.md): start a
`postgres:18.4` container, apply the ten Flyway migrations from `db/migration`,
commit the container as an image, and push it.

```bash
docker commit temp-postgres localhost:5000/football-db:postgres-18.4
docker push localhost:5000/football-db:postgres-18.4
```

## Publish the application images

`k3s/publish-images.ps1` builds each variant and pushes it to the registry.
`-Target All` covers the five that are built from this repository:

```powershell
cd k3s
./publish-images.ps1 -Target All -RegistryHost hetzner-metal:5000
```

Individual targets are `JsNode`, `RustAxum`, `JsWasm`, `RustWasm` and
`RustWasmComponents`. The container variants go through `docker build` and
`docker push`; the Wasm variants through `spin registry push --build --insecure`.

`KotlinSpring` and `KotlinNative` only **tag and push** - they expect
`football-kotlin:spring` and `football-kotlin:native` to exist locally already,
built in the `spring-football` repository with `bootBuildImage`.

Three things about the registry host:

- `-RegistryHost` defaults to `localhost:5000`, which is right for the local k3d
  cluster. For the remote testbed, push to `hetzner-metal:5000`.
- The manifests always reference `localhost:5000/...`, because that is how the
  benchmark node itself reaches zot (see the mirror in `nixos/k3s.nix`). Pushing
  to `hetzner-metal:5000` and pulling from `localhost:5000` are the same registry
  seen from its two ends.
- zot is served over plain HTTP with a frontend at `hetzner-metal:5000`. `spin` is passed `--insecure`, but Docker is
  not: add `hetzner-metal:5000` to `insecure-registries` in the Docker daemon
  configuration, or the push fails on TLS.

  ```json
  "insecure-registries": [
    "hetzner-metal:5000"
  ]
  ```

## Deploy a variant

Each variant has a `-baseline` overlay (fixed replicas) and a `-scaled` overlay
(KEDA HTTP Add-on, scale-to-zero):

```powershell
kubectl apply -k kustomize/environments/axum-baseline
kubectl apply -k kustomize/environments/axum-scaled
```

The `wasm-rust` and `wasm-js` overlays need applying twice on a fresh namespace -
the SpinApp CRD and the resources referencing it race on first apply. The
pipeline script already does this.

## Run the benchmarks

Run these from inside `k6/`: both scripts use paths relative to the working
directory.

Full sweep over every target - deploy, settle, then baseline, coldstart and
scaling in turn:

```powershell
cd k6
./run-pipeline.ps1
```

One target, or a different replay count:

```powershell
./run-pipeline.ps1 -Target wasm-rust -BaselineReplays 10 -ColdstartReplays 30 -ScalingReplays 10
```

`-Idle $true` adds the 10-minute unloaded observation used for the idle-power
baseline. Set any replay count to `0` to skip that scenario.

A single scenario against a single target:

```powershell
./benchmark.ps1 -Target wasm-js -Scenario coldstart -Replays 30
```

What the scenarios do:

| Scenario | Shape |
| --- | --- |
| `idle` | 10 minutes with no load, to measure what the node draws at rest |
| `baseline` | 32 VUs × 3125 iterations = exactly 100,000 requests, fixed replicas |
| `coldstart` | wait for KEDA to scale to zero, cool 30 s, then one single-VU request |
| `scaling` | 13-minute ramping-VU profile (0 → 100 → 0) on the KEDA-scaled deployment |

`baseline` is a *fixed amount of work* rather than a fixed duration: every target
serves the same 100,000 requests, so energy per run and time to completion are
directly comparable. A non-measured warmup run precedes every `baseline` and
`scaling` replay.

Every replay appends `{StartTime, EndTime, Runtime, Framework, Scenario,
Iteration}` to `k6/.output/benchmark_runs.jsonl`. That file is how the analysis
knows which time window belongs to which run, so keep it alongside the metrics.

k6 writes its own histograms straight to VictoriaMetrics over remote write.
`coldstart` and `idle` temporarily patch the KEDA `cooldownPeriod` down to 20 s
and restore it in a `finally` block; if a run is killed hard, check that the
`ScaledObject` got its original value back.

## Analysis

Everything runs through `uv` from `notebooks/`.

First pull the metric ranges out of VictoriaMetrics into parquet. This reads
`../k6/.output/benchmark_runs.jsonl` for the run windows and writes
`parquet/<target>/<scenario>/<metric>_<iteration>.parquet`:

```bash
cd notebooks
uv run marimo edit benchmark_extract.py
```

Then run the analysis notebooks. Each exports its figures to `figures/` as SVG
and PNG, and its tables to `tables/` as CSV and parquet:

```bash
uv run python baseline.py
uv run python coldstart.py
uv run python scaling.py
uv run python breakeven.py
uv run python rtt.py
```

Or open any of them interactively with `uv run marimo edit <file>.py`.

Figure styling is centralized in `common_notebook.py`: `thesis_chart` sets the
fonts, `THESIS_FIGURE_PLOT` pins each figure's plot area so that every figure
prints its labels at the same size in the thesis, and `save_chart` applies both
on the way out. Changing a chart's axis title or subtitle changes how much space
the text around the plot takes, so that figure's entry has to be re-solved.

## Contract tests

The ports are only comparable if they answer identically. `api-contract/` replays
eight requests - every endpoint plus the 404 case - against two or more running
variants and diffs status code, content type, body length and normalized body:

```powershell
cd api-contract
npm install
npm run compare -- --target http://localhost:8080 --target http://localhost:3000
```

See [`api-contract/README.md`](api-contract/README.md) for dumping the raw
responses as artifacts.
